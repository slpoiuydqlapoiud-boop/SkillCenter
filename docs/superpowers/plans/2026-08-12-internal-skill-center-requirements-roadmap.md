# 内部 Skill 管理与分发平台原子需求与里程碑计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 将已确认的内部 Skill 平台任务书拆解为可独立评审、开发、测试和验收的原子需求，并形成 12 周可落地的项目里程碑。

**Architecture:** 平台按身份权限、Skill 治理、市场检索、制品分发、事件统计和平台运营六个业务域拆分；上传扫描与事件聚合均使用异步任务，发布制品进入不可变存储。Web、API、后台任务和客户端通过版本化契约协作，所有查询统一执行可见范围校验。

**Tech Stack:** 本计划不绑定具体编程框架；实现必须具备 Web 门户、API 服务、关系型元数据存储、不可变对象存储、全文搜索、消息队列/异步任务、事件聚合存储，并适配部门现有 SSO、组织目录、安全扫描和监控平台。具体产品选择在 M0 通过架构决策记录固化。

**需求基线：** [内部 Skill 管理与分发平台项目任务书](../specs/2026-08-12-internal-skill-center-design.md)

## 全局约束

- 平台仅负责 Skill 管理、审核、分发和统计，不提供在线创建、编辑、执行、调试或沙箱。
- 上传物为 ZIP，根目录必须包含 `SKILL.md` 和 `skill.json`；发布版本采用语义化版本且不可覆盖。
- 仅面向部门内网用户，通过统一 SSO 登录；权限采用 RBAC 与团队/Skill 数据范围组合控制。
- 默认不采集提示词、输入文件、模型输出、工具参数正文、代码内容、客户数据、密钥和凭据。
- 统计时区固定为 `Asia/Shanghai`，同一上报主体的事件 ID 必须幂等去重。
- 市场搜索 P95 不超过 1 秒，普通查询 P95 不超过 2 秒，安装授权 P95 不超过 1 秒。
- 月度可用性不低于 99.9%；RPO 不超过 15 分钟，RTO 不超过 4 小时。
- 容量验收基线：3,000 用户、2,000 个 Skill、20,000 个版本、日均 100 万调用事件、峰值 300 事件/秒、300 并发在线用户。
- 支持 Chrome、Edge 最新两个主版本；1280px 及以上保持完整功能，1440px 为最佳展示宽度。
- 一期所有 P0 需求必须完成；P1 需求不得阻塞安全、发布、分发、统计和审计主链路上线。

## 1. 拆分与排期规则

### 1.1 原子需求定义

每条需求只描述一个主要角色、一个动作和一个可观察结果，并具备独立验收条件。若一个需求不能在 5 人日以内完成，进入开发前必须继续拆分。

| 字段 | 说明 |
| --- | --- |
| ID | 全局唯一编号，用于需求、代码、测试和发布说明追踪。 |
| 需求 | 单一能力描述。 |
| 验收条件 | 可由测试或产品直接判断通过/失败的结果。 |
| 级别 | P0 为上线门禁；P1 为一期增强。 |
| 规模 | XS=0.5–1 人日，S=1–2 人日，M=3–5 人日；包含实现、自测和必要文档，不含跨团队等待。 |
| 依赖 | 必须先完成或至少冻结契约的需求编号。`—` 表示无产品依赖。 |
| 里程碑 | 该需求必须达到“完成定义”的最晚里程碑。 |

### 1.2 完成定义（DoD）

每条需求只有同时满足以下条件才可标记完成：

- 验收条件对应的自动化或可复现测试通过。
- API、事件或数据 Schema 已版本化并完成兼容性检查。
- 权限、审计、错误状态和日志脱敏已验证。
- 用户可见文案、空状态、加载态和失败态完整。
- 相关监控或业务指标可观测。
- 需求 ID 已关联代码变更、测试用例和发布说明。

### 1.3 推荐代码边界

正式开发仓库建立后，建议按以下边界组织；具体语言和框架不影响需求拆分：

```text
apps/web/                    # 市场、个人中心、审核和管理门户
services/core-api/           # 身份、Skill、版本、审核、收藏、配置
services/validator-worker/   # ZIP 解压、Schema、安全扫描和风险评估
services/distribution/       # 安装授权、清单、签名下载和版本检查
services/event-ingestion/    # 安装/调用事件鉴权、校验、去重和入队
services/analytics/          # 指标聚合、查询和导出
packages/contracts/          # skill.json、事件、API 和错误码契约
packages/authorization/      # RBAC 与数据范围统一策略
infra/                       # 环境、部署、监控、备份和恢复
tests/contract/              # Schema 与跨服务契约测试
tests/e2e/                   # 上传—审核—发布—安装—统计主链路
docs/                        # 用户、维护者、审核员、管理员和运维文档
```

### 3.2 各里程碑详细交付

#### M0：需求与契约冻结（第 1 周）

- [ ] 确认一期 P0/P1 边界和不做事项。
- [ ] 评审 `skill.json`、安装清单、安装事件和调用事件 Schema。
- [ ] 确认风险分级、双人审核、废弃和紧急下架规则。
- [ ] 确认安装、下载、调用、成功率、活跃用户和版本采用率口径。
- [ ] 明确 SSO、组织目录、对象存储、安全扫描、监控和客户端对接人。
- [ ] 输出架构决策记录，确定实现技术栈及环境申请清单。

#### M1：技术底座可用（第 2 周）

- [ ] 建立开发、测试、预生产、生产环境及部署流水线骨架。
- [ ] 打通 SSO 登录、组织同步和角色读取。
- [ ] 建立数据迁移、API 错误、异步任务和审计基础。
- [ ] 完成 Web 全局框架和权限菜单。
- [ ] 发布契约 V1、合规示例包和自动契约测试。

#### M2：上传校验闭环（第 3–4 周）

- [ ] 完成上传、进度恢复、安全解压和资源限制。
- [ ] 完成目录、Schema、一致性、唯一 ID 和 SemVer 校验。
- [ ] 接入敏感信息、恶意文件、依赖/许可证扫描。
- [ ] 生成风险等级、制品哈希、只读预览和校验报告。
- [ ] 完成失败历史、待审核版本和校验链路测试。

#### M3：审核发布与市场 MVP（第 5–6 周）

- [ ] 完成审核领取、筛选、差异、意见、批准和驳回。
- [ ] 完成防自审、跨团队审核和高风险双人审核。
- [ ] 完成不可变发布、最新稳定版和搜索索引刷新。
- [ ] 完成市场搜索、卡片、分页、详情、文档和版本历史。
- [ ] 完成审核通知、审批审计和上传—发布 E2E。

#### M4：分发、个人中心与统计 Beta（第 7–8 周）

- [ ] 完成一次性安装授权、清单、签名下载和哈希校验。
- [ ] 完成一键唤起、CLI 回退、ZIP 下载和客户端状态查询。
- [ ] 完成安装/调用事件批量接入、去重、补报和质量规则。
- [ ] 完成每日汇总、平台/Skill/团队看板和个人记录。
- [ ] 完成版本废弃、紧急下架、授权撤销、影响清单和通知。
- [ ] 完成发布—安装、事件统计和下架 E2E。

#### M5：治理增强与上线候选（第 9–10 周）

- [ ] 完成团队、角色、分类、标签、合集和平台策略配置。
- [ ] 完成受控导出、审计查询、追加保护和数据保留任务。
- [ ] 完成限流、重放防护、XSS/CSRF/越权测试和日志脱敏。
- [ ] 完成监控、告警、备份、完整性巡检和运行手册。
- [ ] 完成帮助文档、浏览器、分辨率、键盘和对比度检查。
- [ ] 冻结 Release Candidate，仅接收阻塞上线的修复。

#### M6：试点验收与生产上线（第 11–12 周）

- [ ] 选取低、中、高风险种子 Skill 及 2–3 个试点团队。
- [ ] 完成客户端兼容、离线补报、峰值事件和市场搜索性能测试。
- [ ] 完成渗透测试、高危清零和中危处置审批。
- [ ] 完成备份恢复及紧急下架演练。
- [ ] 完成 UAT、培训、运维交接、上线审批和回滚演练。
- [ ] 生产上线后观察核心指标，完成首周复盘和 P1 排期更新。

### 3.3 关键依赖路径

```text
Schema 冻结
  → SSO/权限底座
  → 上传与自动校验
  → 审核与不可变发布
  → 搜索/详情
  → 安装授权与客户端联调
  → 事件接入与统计
  → 下架闭环
  → 安全/性能/恢复验收
  → 生产上线
```

任一以下事项延迟会直接影响上线日期：

- SSO 与组织目录接口未在 M1 前提供测试环境。
- 安全扫描接口和规则未在 M2 第一周可用。
- Agent/Codex 安装协议和事件 Schema 未在 M1 冻结。
- 不可变对象存储未在 M2 结束前可用。
- 真实或足够逼真的容量样本未在 M5 前准备完成。

## 4. 工作量与人员规划

### 4.1 粗粒度工作量

原子需求规模仅用于范围比较，不应直接等同于日历工期。按 XS=0.75、S=1.5、M=4 人日换算，预计：

| 工作流 | 参考人日 | 主要角色 |
| --- | ---: | --- |
| 基础架构、身份与授权 | 70–90 | 后端、前端、DevOps、测试 |
| 上传、校验与安全扫描 | 90–115 | 后端、安全、前端、测试 |
| 审核、版本与市场 | 95–125 | 前端、后端、测试、设计 |
| 分发与客户端适配 | 45–60 | 后端、客户端、前端、测试 |
| 事件接入与统计 | 80–105 | 数据/后端、前端、测试 |
| 治理、通知、审计和帮助 | 55–75 | 前端、后端、产品、测试 |
| 安全、运维和专项验收 | 85–110 | 安全、DevOps、测试、研发 |
| **合计** | **520–680 人日** | 不含外部系统排队和正式采购 |

按 2 名前端、3 名后端/数据、2 名测试、1 名 DevOps、1 名产品、1 名设计，以及安全和客户端人员兼职投入，12 周属于高强度目标，成立的前提是复用现有 SSO、扫描、搜索、对象存储和监控能力，并让 P1 作为不阻塞上线的伸缩范围。若安装客户端或事件平台也需从零建设，建议增加 2–4 周或增加 1 名客户端和 1 名数据工程师；不得通过压缩 M5/M6 的安全和验收周期追赶进度。

### 4.2 并行工作流

- 工作流 A：Web 框架、市场、详情、个人中心和治理后台。
- 工作流 B：身份权限、Skill/版本、审核和通知 API。
- 工作流 C：上传校验、安全扫描、制品和分发。
- 工作流 D：事件接入、聚合、统计查询和看板。
- 工作流 E：测试自动化、安全、DevOps、可观测性和文档，贯穿全部里程碑。

## 5. 里程碑评审机制

每个里程碑结束时召开一次门禁评审，只评判证据，不以“完成百分比”代替：

1. 产品负责人核对需求 ID 和验收条件。
2. 技术负责人核对接口、数据迁移、兼容性和未偿技术风险。
3. 测试负责人提交自动化、缺陷和回归证据。
4. 安全负责人在 M2、M3、M5、M6 核对上传、审核、权限和上线风险。
5. 运维负责人从 M1 起核对部署、监控、备份和运行手册。
6. 未通过的 P0 门禁不得带病进入下一生产候选阶段；可在开发分支并行推进不依赖事项。

## 6. 需求变更规则

- 新增一期需求必须具备新 ID、验收条件、优先级、规模、依赖和里程碑。
- 新需求若增加在线执行、在线编辑、公开访问、计费或跨部门多租户，视为范围变更，不进入当前一期。
- M0 后修改 `skill.json`、安装清单或事件 Schema，必须评估客户端兼容和数据迁移。
- M3 后修改发布状态机、权限模型或指标口径，必须重新执行受影响 E2E 和权限测试。
- M5 冻结后仅接受阻塞上线、安全高危、数据错误或不可恢复故障类修改。

## 7. 需求追踪与上线判定

### 7.1 追踪方式

- 需求项：使用本文 ID。
- 开发任务：`<需求ID>-DEV`。
- 测试用例：`<需求ID>-TC-序号`。
- 缺陷：关联一个或多个需求 ID。
- 发布说明：列出本版本完成的需求 ID、已知限制和迁移操作。

### 7.2 一期上线判定

只有同时满足以下条件，项目才可生产上线：

- 所有 P0 原子需求状态为“已验收”或经项目负责人、安全负责人共同批准的明确例外。
- M6 的性能、渗透、恢复、下架、兼容性和 UAT 门禁全部通过。
- P0 缺陷为零；P1 缺陷有负责人、计划完成日期和可接受的临时措施。
- 生产 SSO、组织目录、对象存储、扫描、客户端和监控依赖均通过连通性验证。
- 运维手册、用户指南、维护者指南、审核员指南和管理员指南可用。
- 上线、监控、回滚、值班和首周复盘安排已确认。
